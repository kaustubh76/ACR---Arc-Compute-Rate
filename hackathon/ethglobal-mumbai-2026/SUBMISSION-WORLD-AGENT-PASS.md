## The one-liner

> The agent's wallet holds $0 and its budget lives in a vault. When it asks to
> overpay, the payment is not refused — it is **parked on chain until a verified
> human clears it**, and the refusal paths leave as much public evidence as the
> approval does.

## What it is

An agent with a spending limit has a worst case equal to the limit. Neither a
balance nor a limit answers the question an overcharge actually fails: *is this
a fair price?* Float holds the budget in a vault that recomputes the fair total
itself from ACR's on-chain compute price and refuses anything above a band.

**Agent Pass is what happens at the edge of that band.** Over the per-request
threshold the request is not denied. A checkpoint opens on chain; a human
completes a *fresh* World ID device-flow authentication; the backend validates
that ID token against a fixed ladder; and only then does a single-use EIP-712
approval let the vault move USDC.

Three properties are the whole design:

1. **An approval widens the band. It never removes it.** A person can authorise
   paying more than usual. Nobody — including the approver — can authorise
   paying an unpriced amount to an unapproved seller. `executeApproved`
   re-checks band, cap and print *after* the signature is accepted, so a valid
   human and a refused payment is a real and tested state.
2. **The approver cannot invent a spend.** The approval commits to
   `FloatApproval(uint256 id, bytes32 reqHash, uint64 expiresAt, bytes32
   humanBinding)`. The vault compares the request against the hash it opened the
   checkpoint with, within its TTL, once. Replay, re-aim at another seller, a
   different amount, a fabricated checkpoint id and a signature from the wrong
   key are each refused on chain, each with its own test.
3. **A refusal is evidence, not silence.** Denial, expiry and a failed
   verification are each written on chain as `CheckpointResolved`. A treasury
   whose refusals are invisible cannot be audited.

### 3 · An unsuccessful path where the protected action does not occur — **LIVE, and MECHANISM six ways**

Six of them, each asserted against the chain rather than against a log, and the
test names are the claim:

```
uv run pytest services/index_api/tests/test_floatgate_onchain.py
```

- `test_a_denial_is_recorded_on_chain_and_moves_nothing` — the human says no, the
  denial is recorded on chain, the seller's balance is unchanged.
- `test_an_expired_checkpoint_moves_nothing` — the window closes unused.
- `test_a_signature_from_the_wrong_key_moves_nothing` — a valid signature from
  the wrong signer.
- `test_a_replayed_approval_is_refused_by_the_chain` — single-use enforced by the
  vault, not by us.
- `test_a_fabricated_checkpoint_id_is_refused`.
- `test_a_real_checkpoint_executed_for_another_agent_is_refused` — the whole
  transaction rolls back and the checkpoint stays open.

**And LIVE, measured 2026-11-06 against World's own issuer.** A
`REHEARSE_WORLD=live` run opened a real device authorization
(`XA4SF-RKRGB`), the human did not approve it inside the window, and the run
asserted the consequence against the chain rather than reporting a shrug:

```
✗ nothing was approved before the deadline
✓ no token, so NOTHING MOVED · seller still 0.000000 USDC
✓ checkpoint #1 is still OPEN, not consumed and not spent
✓ the protected action did not occur, and the chain is the witness
```

That is the cancelled/expired path end to end on a real credential: World issued
a genuine authorization, no approval came back, and **the money did not move**.
The checkpoint stays `OPEN` rather than being consumed, so a later approval is
still possible — an unsuccessful attempt is not a destroyed payment. A timeout,
a refusal and a cancellation all arrive at that same assertion.

### 4 · Validated in a secure backend, with no secret or unvalidated response trusted — **MECHANISM**

```
uv run pytest services/index_api/tests/test_worldauth.py services/index_api/tests/test_worldflow.py services/index_api/tests/test_floatgate.py
```

**The secret never leaves the server, and never enters a body it was not meant
for:** `test_the_secret_authenticates_with_basic_and_never_reaches_the_body`.
It lives only in a gitignored `.env`.

**The device code is a bearer credential and is treated as one:**
`test_neither_the_device_code_nor_the_id_token_reaches_the_public_view`,
`test_the_device_code_never_appears_in_the_public_view`,
`test_a_finished_checkpoint_forgets_its_device_code`,
`test_the_public_view_carries_only_the_permitted_fields`. The browser is told the
user code and nothing else; the token is never sent to a client.

**No unvalidated client response is ever authorization.** The validator pins
`alg` to RS256 and refuses the two attacks that a naive verifier accepts:
`test_a_signature_from_another_key_is_refused`, and
`test_a_token_signed_with_the_public_key_as_an_hmac_secret_is_refused` — the
`alg` confusion where the RSA public key is used as an HMAC secret. `alg:none`
is refused by the same pin. The chain is the final authority regardless: the
vault verifies the EIP-712 approval itself and reverts `bad approval` on
anything else.

## Secure backend validation

The ID token is validated server-side against **nine named refusals, reported
in a fixed order, naming the first rung that failed rather than the last.**

```
malformed_token · bad_signature · wrong_issuer · wrong_audience · expired
assurance_not_accepted · amr_not_accepted · auth_time_outside_window
not_the_enrolled_treasurer
```

The count is pinned by a test rather than by this sentence:
`worldauth.REASONS` is the tuple and `test_every_named_reason_is_reachable`
asserts set-equality between it and the reasons nine fixtures actually produce,
so the prose cannot drift from the code without a red test.

Four decisions in there are worth defending out loud:

- **The algorithm is pinned, not read from the token.** `alg: none` and
  HS256-signed-with-the-public-key are both refused as `bad_signature` — the two
  classic JWT forgeries, each with its own fixture.
- **Freshness is measured against when the checkpoint opened**, not against
  "now". A token minted before the payment existed cannot approve it.
- **Reporting the first failing rung is deliberate.** A stale `auth_time`, an
  unverified account and the wrong person are three problems with three fixes,
  and collapsing them into "verification failed" is what makes an approval gate
  undebuggable.
- **503 is never an approval, and a 429 ends the attempt.** `slow_down` widens
  every later interval, not just the next. The status check happens *before* the
  body is parsed, so an unparseable error page cannot be mistaken for a verdict.

A device code never appears in any serialisation of a checkpoint: it is held in
a separate map keyed by checkpoint id, which is a structural guarantee rather
than a rule someone has to remember.

## The same identity also opens a budget, which is new

A verified human approving a parked payment and a verified human being *given* a
small budget are the same question asked twice: **is this one unique person, and
are they who they were last time.** Agent Pass answers both, so the guest budget
now runs on it:

```
scripts/world_id.py guest          # the device flow, then a budget on chain
scripts/world_id.py guest --fake   # the same path, no credential, no phone
```

`keccak256("acr.guest::" ‖ iss ‖ 0x1f ‖ sub)` is the budget's id — deliberately
the same preimage shape as `treasurerBinding`, differing only in the domain
prefix inside the hash, so a treasurer and a guest can never collide. The `sub`
is pairwise per client and stable, so **one human is one budget by
construction**: the chain answers "has this person already been issued one" from
the id alone, and `registerGuest` reverts `agent exists`. Nothing of the
identifier reaches the chain but that hash, and nothing reaches a log but
`••••` and three characters.

**This replaced a design that a provider change deleted under us.** The budget
was built on World ID Selfie Check, which the World team confirmed on 2026-11-06
is no longer offered. We did not patch around it: the substitution needed **no
new function, no change to `guest_agent_id`, and nothing whatsoever on chain**,
because the thing being hashed was always just "a stable per-human string". The
credential it now rests on is **orb**, which is stronger than the one withdrawn,
and the attacker-cost inequality in the withdrawn write-up only widens — a
rented orb identity costs more than the `$10` floor that argument used, against
the same 2 USDC a day.

**One argument differs from every other command in this entry, and it is the
whole point:** `treasurer=None`. Everywhere else an approval is held to the one
enrolled treasurer and a different human is refused
`not_the_enrolled_treasurer`. A public door must accept *any* verified human and
give each their own budget, so that check is deliberately absent there and the
assurance class carries the weight instead. It is one line, and it is the line
that separates "the treasury's owner" from "a stranger at the door".

**What is not yet true.** The public vault's `guestRegistrar` is still the
deployer, so this command stands down against it by name and prints the single
owner transaction that fixes it. The identity half above is proven either way,
and `--fake` demonstrates the whole path offline.

## Honest limits

- **`access_denied` means three different things** and the provider cannot tell
  us which: the human refused, the essential assurance class was unmet, or the
  subject did not match. We record it as DENIED with a reason naming all three.
  We never report it as "the human denied it", because two thirds of the time
  that would be a guess. This is also our top debrief item's sibling.
- **The approval screen cannot say what is being approved.** World's device
  profile is explicit that `binding_message` and action terms are unsupported
  and are not displayed or signed into the token, so the signed token attests
  *who* authenticated and *when*, never *what* they agreed to. We therefore
  render the amount, seller, fair price and user code ourselves and bind them
  server-side. This is the single improvement we would most like, and it is
  argued in the debrief from World's own documentation rather than from opinion.
- **The executor can resolve any open checkpoint, including writing EXPIRED over
  one a human already signed.** This is finding **F8** in our own Arc Studio
  audit (`float/studio/README.md`), accepted and not repaired. It qualifies the
  containment claim honestly: the approver cannot invent a spend, but the
  executor can nullify an approval. Narrowing `resolveCheckpoint` to the
  checkpoint's own opener is the fix and it is not in this submission.
- **The human gate covers payments and policy, not the treasury's yield path.**
  This treasury also earns: idle float is parked into a yield sleeve. But
  `rebalance(uint256)` is `require(msg.sender == keeper)` and nothing else, with
  no signature, no per-transaction cap and no cooldown, and `openCheckpoint`
  accepts only the spend and policy kinds, so **a sleeve move cannot be parked
  for a human even in principle** — the approval machinery has no shape that
  fits one. Re-pointing a sleeve is finding **M5** in `docs/SECURITY-AUDIT.md`,
  accepted rather than repaired. The only share cap (30%) and minimum interval
  (10 minutes) live off chain in `float/src/bin/keeper.ts`, so a keeper key
  calling `rebalance` directly bypasses both and the contract does not notice.
  Measured on the public vault rather than assumed: `reserve()` is the zero
  address, so the reserve share of every rebalance is computed and then stays in
  the buffer. What this submission *does* add is a press that refuses to run
  when the vault's keeper is one of its own gate keys
  (`test_the_gate_refuses_when_the_keeper_is_also_our_executor`), because the
  contract permits that and forbids only `approver != executor`; and a
  `/float/approve` that prints what the human governs beside what moves on a
  single key. Putting the yield path behind a checkpoint needs a third
  checkpoint kind and a redeploy, and it is not in this submission.
- **The chain never requires a treasurer binding, so the human half of an
  approval is enforced off chain.** `_consumeApproval` feeds `treasurerBinding`
  into the digest whatever it holds, and guards only the *approver* against
  zero — rightly, since `ecrecover` returns `address(0)` on a malformed
  signature. But a binding of zero is itself a valid signature target that
  identifies nobody, so on an unenrolled vault the approver's signature still
  authorises the payment while attesting to no human at all. Nothing an
  attacker reaches: it needs the approver's key, and the approver cannot invent
  a request. What it means is that "a verified human cleared this" rests on
  `vault_status()` refusing that state and the gate refusing to park into it,
  not on the contract. Proved rather than asserted, on a vault deployed with no
  binding, by `test_an_unset_binding_leaves_the_human_half_of_an_approval_vacuous`
  — which also records the operational consequence: the public vault's binding
  is zero until enrollment, so the order the two roles are set in matters.
- **Neither issuer advertises a Selfie assurance class.** `acr_values_supported`
  is exactly `orb` and `orb-face` on both `auth.world.org` and
  `sandbox.auth.world.org`, measured. The step-up guide documents a `selfie`
  class that neither issuer offers, so we request `orb` alone: naming an
  unadvertised class in an *essential* claim is not a preference a provider
  ignores, it is a requirement it cannot meet. The gate cross-checks its
  configured classes against discovery and stands down rather than sending a
  request that cannot succeed.
- **A policy change is held to its own assurance list, but our shipped default
  is not a stronger one.** `requirePolicyCheckpoint` really does gate
  `setPolicy`, `setAgent` and `allowSeller` over a hash the chain derives
  itself, and `make rehearse-float` leg 11 shows an unapproved change refused,
  a face verification accepted and the band moving from 10% to 12% only once a
  person signed. But the default list is `orb-face, orb`, which accepts a plain
  orb token: it is a superset of the payment list, so what the default actually
  gives is a second, independent, *fresh* verification rather than a higher
  class. Narrowing it to `orb-face` alone makes the separation real, and the
  rehearsal demonstrates that configuration. We ship the wider default because
  a treasurer with no face credential would otherwise be locked out of their
  own policy permanently, which is a worse failure than a weaker gate.
- **The guest daily cap is fixed at deploy** (`guestDailyCap`, constructor-only).
  Changing it is a redeploy. We state it because "revocable budget" could
  otherwise be read as "adjustable budget".
- **The identity of the human the chain holds approvals to** is
  `treasurerBinding = keccak256("acr.treasurer::" ‖ iss ‖ 0x1f ‖ sub)`, set
  one-shot from zero. On the public deployment it is **still zero**, which means
  the chain does not yet pin a particular person and the server-side ladder is
  what enforces identity. Setting it requires the enrollment run, and a *wrong*
  value is worse than none — the approval would stay valid and bind to the wrong
  person — so it is set last, after a dry run proves the digest round-trips.

## Status of the live run, stated plainly

**The live leg ran.** On 2026-11-06 a registered client on World's **sandbox**
issuer, `sandbox.auth.world.org`, issued two real ID tokens to a real person
holding a phone, and both cleared the nine-rung ladder.

One scoping note we would rather state than let a reader infer: sandbox is where
our client lives, and **we did not establish whether the production portal would
have opened to us.** We read that it does not open to a non-Orb developer
account, planned around that, and never tested it. The same client is refused by
production with HTTP 401, which proves only that it is not registered there.

It is irreversible in a way worth stating plainly. The issuer string is hashed
into `treasurerBinding`, and `setTreasurerBinding` accepts a value exactly once
from zero, so the public vault becomes permanently a sandbox identity — the same
human against the two issuers produces two unrelated bindings, and a production
token could never clear a payment on that vault afterwards. We are setting it
knowing that, because a sandbox credential we can actually obtain is worth more
than a production one we cannot. Concretely:

- Everything above marked with a command **runs today**, with a token this
  repo mints itself: a genuine RS256 ID token from a locally generated key, run
  through the same nine-rung ladder a live token goes through. **What is
  synthetic is the issuer, not the validation.**
- **And the protocol itself now runs, not only the validation.**
  `REHEARSE_WORLD=fake make rehearse-float` stands up an OIDC issuer on a local
  port and obtains the token **over HTTP**: discovery and its issuer check, the
  essential-`acr` claims parameter as a `values` array, the device grant, the
  poll table including an `authorization_pending`, a JWKS fetched from the
  advertised `jwks_uri`, the nine rungs, and a payment released on chain by a
  token nothing local minted. We added it because the honest answer to "is the
  device flow tested" was no: the rehearsal injected a validator and the unit
  tests stub the transport with a JWKS that has no modulus, so the most
  protocol-heavy file in this entry had no end-to-end witness. It has one now
  (`tests/test_fake_agent_pass.py`), and the same leg runs against World
  unchanged the day a client exists.
  **This is not evidence about World.** A local issuer says yes because it was
  written to. It proves the code between our configuration and a token, which is
  the part that is ours to get right.
- **And then a real issuer did it.** `make world-probe` and `make world-enroll`
  each opened a device authorization against sandbox, a person approved in World
  App, and a genuine RS256 token came back and passed every rung: `acr` orb,
  `auth_time` after the checkpoint opened, the signature verified against a JWKS
  fetched from the advertised `jwks_uri`. Discovery answers in **1.6 s** (median
  of five) and the two end-to-end runs took **84.0 s** and **49.4 s** — figures
  the human dominates, since the protocol floors the poll interval at five
  seconds and our own share is the sub-second validation at the end. The
  debrief's two device-flow rows are now measurements. Its third was a **Selfie
  Check** row and is now marked unmeasurable, because that check no longer
  exists — which is what withdrew our second entry.
- **The live token also found something we had only reasoned about.** It came
  back with `amr` = `["pop","user","mfa"]` — the passkey shape, which World's
  own docs note *"does not assert a fresh World proof"*. So `acr` said orb while
  the authentication was a passkey unlock. Our spend path accepts that, which is
  correct: orb assurance is what it asks for. Our **policy** path would refuse
  this exact token, because it requires `face` in `amr` and forbids `mfa`. That
  separation was built from the documentation months ago and this is the first
  token to prove it bites — the same credential that legitimately cleared a
